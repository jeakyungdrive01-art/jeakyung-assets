# 역할과 권한 매트릭스

## 역할

1. `super_admin` — 최고 관리자
2. `admin` — 관리자
3. `department_head` — 부서장
4. `team_lead` — 팀장
5. `employee` — 직원

역할은 직급·직책과 별개다. 한 사용자의 최종 권한은 역할, 소속 조직, 리소스별 정책과 명시적 예외를 서버에서 조합해 판정한다.

## 판정 원칙

- 메뉴를 숨기는 것은 편의 기능이며 보안이 아니다.
- 클라이언트, 서버 함수와 Supabase RLS가 동일한 권한 개념을 사용한다.
- 기본값은 거부이며 명시적으로 허용된 작업만 수행한다.
- 최고 관리자 권한 부여·회수, 최종 삭제와 권한 변경은 재인증과 감사 로그를 요구한다.
- 한 사용자는 여러 역할을 가질 수 있으며 `user_role_assignments`의 `(user_id, role_code)`를 유일하게 유지한다.
- 일반 관리자는 `admin`, `super_admin`을 부여할 수 없고 최고 관리자만 관리자 계열 역할을 부여한다.
- 기본 역할을 자동 부여하지 않으며 첫 최고 관리자는 별도 1회성 SQL로만 부트스트랩한다.
- 관리자 메뉴는 Auth Context의 DB 역할로 표시하고 직접 URL은 관리자 Route와 RLS·RPC가 다시 차단한다.

게시판별 권한은 [`29_BOARD_SYSTEM.md`](29_BOARD_SYSTEM.md), 서버 보안은 [`31_SECURITY_AND_RLS.md`](31_SECURITY_AND_RLS.md)를 따른다.

## 활성 역할 정책

- 사용자는 활성 상태의 여러 배정 역할을 보유하되 권한 합산 없이 서버에 저장된 `active_role_code` 하나로 업무 권한을 판정한다.
- 모든 승인 직원은 최소 `employee` 역할을 유지한다. 기존 최고 관리자에는 데이터 손실 없이 `employee`를 추가하고 기존 최고 관리자 역할을 초기 활성 역할로 유지한다.
- 활성 역할은 계정 단위로 유지되어 새 세션과 다른 기기에서도 마지막으로 서버에 저장된 값이 적용된다. 클라이언트 state와 localStorage는 권한 근거가 아니다.
- `admin`·`super_admin` 메뉴와 RPC는 해당 역할을 활성화했을 때만 허용한다. 직원 모드에서는 고권한 역할을 보유하고 있어도 관리자 권한을 사용하지 않는다.
- 역할 해제 시 현재 활성 역할이면 남은 권장 역할로 원자적으로 전환한다. 마지막 활성 최고 관리자 역할과 마지막 최고 관리자의 퇴사 처리는 차단하고 시도 자체를 감사 로그에 남긴다.
